# Java 예외 처리 복습 노트

## 1. 왜 예외 처리가 필요한가

처음에는 실패 여부를 문자열이나 숫자로 반환해도 충분하다고 생각했다.

예를 들어 외부 서비스에 연결한 뒤 결과로 `"success"` 또는 `"connectError"`를 반환하게 만들 수 있다.  
그런데 이 방식은 호출하는 쪽에서 매번 결과값을 검사해야 한다.

```text
String result = client.connect();

if (!result.equals("success")) {
    return;
}
```

코드가 짧을 때는 별문제가 없어 보이지만, 연결, 전송, 종료처럼 단계가 늘어나면 정상 흐름 사이에 오류 확인 코드가 계속 끼어든다.

내가 느낀 가장 큰 문제는 두 가지였다.

- 실제로 하고 싶은 작업보다 오류 검사 코드가 더 눈에 띈다.
- 중간에 `return`이 실행되면 반드시 처리해야 하는 정리 작업을 놓칠 수 있다.

결국 예외 처리는 단순히 오류 메시지를 보여 주는 기능이 아니라,  
**정상적으로 실행되는 흐름과 실패했을 때의 흐름을 분리하기 위한 장치**라고 이해했다.

---

## 2. 예외가 발생하면 실행 흐름이 바뀐다

메서드 안에서 예외가 발생하면 아래의 코드는 그대로 이어서 실행되지 않는다.

```text
client.connect();
client.send(data);
client.disconnect();
```

위 코드에서 `send()` 중 예외가 발생하면 `disconnect()`까지 도달하지 못할 수 있다.

이 부분을 공부하면서 알게 된 점은,  
예외 처리를 했다고 해서 무조건 안전해지는 것이 아니라는 것이다.

중요한 것은 다음이다.

1. 어디에서 예외가 발생할 수 있는지 확인한다.
2. 그 예외를 현재 메서드가 처리할 수 있는지 판단한다.
3. 반드시 실행되어야 하는 정리 로직을 따로 보장한다.

---

## 3. `throw`와 `throws`는 역할이 다르다

처음에는 두 키워드가 비슷해서 자주 헷갈렸다.

### `throw`

예외 객체를 직접 만들어 발생시킨다.

```text
throw new IllegalStateException("연결되지 않은 상태입니다.");
```

### `throws`

현재 메서드에서 발생한 예외를 호출한 쪽으로 넘길 수 있다고 선언한다.

```java
public void send() throws IOException {
    // ...
}
```

내가 기억하는 방식은 간단하다.

- `throw`: 지금 예외를 발생시킨다.
- `throws`: 이 메서드 밖으로 예외가 전달될 수 있다.

---

## 4. 체크 예외와 언체크 예외

Java 예외를 공부할 때 가장 많이 헷갈린 부분이었다.

### 체크 예외

`Exception`을 상속받지만 `RuntimeException` 계열은 아닌 예외다.

체크 예외는 컴파일러가 처리 여부를 확인한다.  
따라서 예외를 잡지 않으면 `throws`로 밖에 전달해야 한다.

```java
public class DataReadException extends Exception {

    public DataReadException(String message) {
        super(message);
    }
}
```

체크 예외의 장점은 예외 처리를 빠뜨리기 어렵다는 점이다.  
반대로 호출 계층마다 `throws`가 계속 이어지면 코드가 번거로워질 수 있다.

그래서 나는 체크 예외를 볼 때 다음을 먼저 생각하려고 한다.

> 호출한 쪽에서 이 문제를 실제로 복구할 수 있는가?

복구할 수 있다면 체크 예외가 의미가 있지만,  
결국 모든 계층에서 처리하지 못하고 계속 전달만 한다면 굳이 체크 예외여야 하는지 다시 볼 필요가 있다.

---

### 언체크 예외

`RuntimeException`을 상속한 예외다.

```java
public class DataLoadException extends RuntimeException {

    public DataLoadException(String message, Throwable cause) {
        super(message, cause);
    }
}
```

언체크 예외는 `throws`를 생략할 수 있다.  
잡지 않으면 자동으로 호출한 쪽으로 전달된다.

언체크 예외는 편하지만, 컴파일러가 처리 여부를 강제하지 않는다.  
따라서 예외가 발생할 수 있다는 사실을 코드 구조나 문서에서 알 수 있게 만드는 것이 중요하다고 느꼈다.

---

## 5. 예외는 어디에서 처리해야 할까

예외가 발생한 곳에서 무조건 처리해야 하는 것은 아니다.

예를 들어 파일 읽기 코드에서는 파일을 읽지 못했다는 사실은 알 수 있다.  
하지만 사용자에게 다시 입력을 요청할지, 기본값을 사용할지, 프로그램을 종료할지는 상위 계층이 더 잘 안다.

그래서 예외를 처리할 위치는 다음 기준으로 판단하는 것이 좋다고 정리했다.

- 현재 계층이 복구 방법을 알고 있으면 처리한다.
- 복구 방법을 모르면 호출한 쪽으로 전달한다.

예외를 잡고 아무것도 하지 않는 코드는 피해야 한다.

```text
try {
    service.execute();
} catch (Exception e) {
    // 아무 처리도 하지 않음
}
```

이렇게 하면 프로그램은 조용해 보이지만, 실제 실패 원인을 찾기 어려워진다.

---

## 6. 예외를 변환할 때 원인을 남겨야 한다

하위 계층의 예외를 상위 계층에서 이해하기 쉬운 예외로 바꾸는 경우가 있다.

```text
try {
    return Files.readString(path);
} catch (IOException e) {
    throw new DataLoadException("데이터 파일을 읽지 못했습니다.", e);
}
```

여기서 `e`를 함께 전달하는 이유는 원래 실패 원인을 남기기 위해서다.

원인 예외를 버리면 나중에 로그에서 다음 정보를 잃을 수 있다.

- 파일이 존재하지 않았는지
- 접근 권한이 없었는지
- 인코딩 문제가 있었는지
- 실제로 어느 줄에서 실패했는지

예외를 새로 감싸더라도 원인 예외는 최대한 유지하는 편이 좋다고 생각한다.

---

## 7. `try-catch`로 정상 흐름과 예외 흐름을 분리한다

예외를 사용하면 정상 코드와 실패 코드를 비교적 분명하게 나눌 수 있다.

```text
try {
    client.connect();
    client.send(data);
} catch (ClientException e) {
    System.out.println("처리 실패: " + e.getMessage());
}
```

`try` 안에는 원래 하려던 작업을 적고,  
`catch`에는 실패했을 때의 대응을 적는다.

반환값 방식보다 정상 흐름을 읽기가 쉬워진다는 점이 가장 큰 장점이라고 느꼈다.

다만 `catch`를 너무 넓게 잡으면 문제가 생길 수 있다.

```text
catch (Exception e) {
    // 모든 예외를 같은 방식으로 처리
}
```

모든 예외를 한 번에 잡으면 편해 보이지만,  
입력 오류와 시스템 오류를 구분하지 못하게 될 수 있다.

가능하면 필요한 예외만 구체적으로 잡는 것이 좋다.

---

## 8. 예외 계층을 활용하는 이유

예외도 상속 구조를 만들 수 있다.

```text
ClientException
├─ ConnectException
└─ SendException
```

이렇게 나누면 연결 실패와 전송 실패를 서로 다르게 처리할 수 있다.

```text
try {
    client.execute();
} catch (ConnectException e) {
    // 연결 재시도
} catch (ClientException e) {
    // 그 밖의 클라이언트 오류
}
```

구체적인 예외를 먼저 잡고, 상위 예외를 나중에 잡아야 한다.

내가 이해한 예외 계층의 목적은 단순히 클래스를 많이 만드는 것이 아니다.

> 호출자가 서로 다른 방식으로 처리해야 할 때 예외 타입을 구분하는 것

처리 방법이 모두 같다면 예외를 너무 세분화할 필요는 없다.

---

## 9. `finally`는 정리 작업을 보장한다

외부 자원은 예외가 발생하더라도 정리되어야 한다.

```text
try {
    resource.open();
    resource.use();
} finally {
    resource.close();
}
```

`finally`는 정상 실행, 예외 처리, 예외 전파 상황에서도 실행된다.

그래서 연결 해제나 파일 닫기처럼 반드시 실행해야 하는 작업을 넣을 수 있다.

하지만 자원이 `AutoCloseable`을 구현하고 있다면 `try-with-resources`가 더 단순하다.

```text
try (BufferedReader reader = Files.newBufferedReader(path)) {
    return reader.readLine();
}
```

이 방식을 사용하면 직접 `finally`에서 닫지 않아도 자원 정리를 보장할 수 있다.

---

## 10. 예외를 잡았다고 항상 해결된 것은 아니다

예외를 `catch`로 잡으면 프로그램이 종료되지 않을 수 있다.  
하지만 단순히 잡았다는 이유만으로 문제가 해결된 것은 아니다.

다음 내용을 함께 확인해야 한다.

- 사용자에게 다시 시도할 기회를 줄 것인가
- 오류를 로그로 남길 것인가
- 기본값으로 계속 진행할 것인가
- 현재 작업을 중단할 것인가
- 사용한 자원을 정상적으로 반납했는가

예외 처리는 문법보다 정책이 더 중요하다는 생각이 들었다.

---

## 11. 공부하면서 정리한 실수하기 쉬운 부분

### `throw`와 `throws`를 혼동하는 것

하나는 실제 예외 발생이고, 다른 하나는 메서드 선언이다.

### 예외를 잡고 무시하는 것

오류가 없는 것처럼 보이지만 문제를 숨기게 된다.

### 원인 예외를 버리는 것

새 예외를 만들더라도 기존 예외를 `cause`로 남기는 것이 좋다.

### 자원 정리를 정상 흐름에만 두는 것

중간에 예외가 발생하면 실행되지 않을 수 있다.

### 너무 넓은 예외 타입을 먼저 잡는 것

상위 타입을 먼저 잡으면 하위 타입별 처리가 불가능해진다.

### 언체크 예외는 아무 처리도 필요 없다고 생각하는 것

컴파일러가 강제하지 않을 뿐, 필요한 경우에는 여전히 잡고 처리해야 한다.

---

## 12. 내가 이해한 예외 처리 기준

### 체크 예외를 고려하는 경우

- 처리 여부를 반드시 강제할 필요가 있다.

### 언체크 예외를 고려하는 경우

- 대부분의 호출자가 직접 복구하기 어렵다.
- 여러 계층에 `throws` 선언이 반복되는 것을 피하고 싶다.
- 잘못된 상태나 프로그래밍 오류를 나타낸다.

### 예외를 현재 계층에서 잡는 경우

- 실제로 복구할 수 있다.
- 사용자 응답이나 재시도 여부를 결정할 수 있다.

---

## 13. 핵심 정리

- 반환값으로만 실패를 처리하면 정상 흐름과 오류 흐름이 섞이기 쉽다.
- 예외를 사용하면 정상 코드와 실패 코드를 분리할 수 있다.
- `throw`는 예외 발생, `throws`는 예외 전달 선언이다.
- 체크 예외는 처리 또는 전파가 강제된다.
- 언체크 예외는 자동으로 전파될 수 있다.
- 예외는 발생한 곳보다 복구 방법을 아는 곳에서 처리해야 한다.
- 예외를 변환할 때 원인 예외를 유지하는 것이 좋다.
- 구체적인 예외를 먼저 잡고 상위 예외를 나중에 잡는다.
- 외부 자원은 예외 발생 여부와 관계없이 정리해야 한다.
- 예외 처리는 문법보다 처리 정책을 정하는 일이 더 중요하다.
